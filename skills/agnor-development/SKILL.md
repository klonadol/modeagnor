# Разработка AGNOR

## Текущее состояние

AGNOR — companion-мод Minecraft с автономными 3D-персонажами, диалогом, памятью, голосом и процедурным поведением. Первый продукт должен быть полезен без переноса авторского мира и Create. База: Minecraft 1.21.1, Fabric, Java 21; сервер хоста — источник истины.

Текущий порядок и критерии готовности задаёт только ROADMAP (P0–P10), факт выполнения — журнал/отчёты и код. P0 имеет ограниченную границу bootstrap; renderer/storage/motion не являются её gates. Проверяй актуальный статус перед задачей. Не считай будущие компоненты готовыми по описанию в Blueprint.

## Правила написания кода

1. **Следуй контракту компонента.** Найди входы, выходы, владельца состояния и потребителей в Blueprint. Не вводи параллельную схему или второй источник истины.
2. **Соблюдай границы среды.** main содержит common/server и сетевые DTO; client — UI, рендеринг, локальное аудио и визуальную интерполяцию. Main не импортирует client. Клиент не является источником истины памяти, решений или изменений мира.
3. **Меняй игровой мир на server thread.** Сетевые callbacks валидируют вход и отправителя, затем планируют изменение мира в правильном server-thread контексте. Не выполняй IO, HTTP, LLM или тяжёлую работу в callback/тике.
4. **Ограничивай фоновые задачи.** Для внешних вызовов задавай timeout, bounded queue, отмену и обработку отказа. Отказ API не должен останавливать сервер.
5. **Проектируй сетевые контракты явно.** Версионируй DTO, ограничивай размеры и валидируй значения на границе. Бери identity/права из доверенного контекста. Определи поведение повторов и идемпотентность эффектов.
6. **Изолируй данные.** Привязывай состояние к world/NPC/player scope. Используй Storage Facade, когда он реализован; не обходи транзакции и миграции. Секреты и приватные данные не попадают клиентам, Content Packs или логам.
7. **Реализуй вертикальный поток.** Соединяй событие/запрос, серверное решение, эффект, сетевое отображение и сохранение. Принимай законченный ограниченный срез отдельно; статус всей фазы требует её итоговой интеграции. Runtime feedback не обязывает одновременно реализовывать всех участников.
8. **Делай ошибки конечными и диагностируемыми.** Валидируй данные на входе, не проглатывай исключения, ограничивай retry и предотвращай feedback loops.
9. **Сохраняй совместимость.** Добавляй только необходимые зависимости и закрепляй версии. Проверяй dedicated-server classloading. Не связывай ядро с необязательными интеграциями; используй адаптеры на границе.
10. **Различай реализацию и проверку.** Сборка доказывает компиляцию, но не работу функции. Указывай фактически проверенные сценарии и непроверенные ограничения.
11. **Переиспользуй подходящие ассеты.** Проверяй формат, риг, возможности и права. Временные ассеты учитывай в реестре и не включай в публичные артефакты.

## Рабочий цикл

1. Определи фазу и критерий задачи по Roadmap. Проверь Blueprint, ADR и код.
2. При открытом выборе сначала проверь, мешает ли он текущей задаче. Используй первичные источники; ограниченный spike нужен лишь при недостатке evidence. Задай вопрос, минимальный fixture и условие остановки. Renderer — перед 3D, storage — перед первой сохраняемой NPC; не закрывай все Open-вопросы Blueprint заранее.
3. Измени минимально связный участок в правильном source set. Добавь тесты контракта и отказных случаев, если они уместны.
4. Запусти относящиеся к задаче проверки через Gradle Wrapper. В Windows используй `powershell -File scripts/dev.ps1 <task>`, если задача поддерживается скриптом; иначе вызывай Wrapper напрямую.
5. Проверь diff, source-set границы, случайные локальные файлы, секреты и соответствие документации.
6. Для завершённой логической работы создай `docs/reports/YYYY-MM-DD-NNN-short-title.md` по шаблону и добавь запись в начало `docs/DEVELOPMENT_LOG.md`. Обновляй архитектуру, roadmap и ADR только если изменились их предметы.

## Подбор проверок

Различай А (существующий код), Б (ограниченный риск текущего решения), В (интеграция после появления всех участников). Не включай В в ранние gates. Не повторяй всю сборку/два клиента/provider tests для каждого изменения документации или чистого алгоритма. Выбирай проверки по изменённому поведению.


- Java/common: сборка, целевые unit-тесты и отсутствие client-only ссылок из main.
- Сеть: сериализация, пределы, версия, неверные/повторные запросы, права отправителя и server-thread поведение.
- Хранилище: миграции, транзакции, повторный запуск и изоляция scope.
- Client/render: запуск клиента и dedicated-server classloading.
- NPC/runtime: путь целиком в интегрированном и dedicated server с несколькими игроками; проверяй перезапуск для сохраняемого состояния.
- Внешние сервисы: timeout, недоступность, отмена, лимиты очередей, отсутствие блокировки тика.

Запускай проверки, относящиеся к работе, и сообщай команды с результатом. Не подменяй runtime-проверку сборкой или unit-тестом.

## Архитектурные изменения

При изменении границ компонентов, формата данных/сети, ownership, порядка фаз или принятого решения создай ADR по шаблону и обнови `DECISIONS.md`. При необходимости синхронно обнови `ARCHITECTURE.md`, `ROADMAP.md` и индекс. Старый ADR помечай Superseded со ссылкой на замену, сохраняя историю.
