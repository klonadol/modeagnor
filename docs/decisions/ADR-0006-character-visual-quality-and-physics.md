# ADR-0006: Целевое качество 3D-персонажей и физики движения

- **Статус:** Accepted (целевой уровень качества); выбор runtime renderer остаётся открытым
- **Дата:** 2026-11-02
- **Область:** Rendering / Animation / Character Art / Performance

## Контекст

Пользователь выбрал максимально высокое качество 3D-аниме-персонажей с уровнем визуальной выразительности современной stylized action-RPG, ориентир по динамике и вторичной физике — Zenless Zone Zero (ZZZ).

Это означает не просто наличие скелета и нескольких анимаций. Нужны плавная деформация полигональной модели, выразительное лицо, смешивание анимаций, процедурное управление позой и art-directed secondary motion для волос, одежды и аксессуаров.

## Решение

Зафиксировать следующий целевой профиль.

### Геометрия и риг

- Полноценная гладкая polygon mesh, не кубическая модель Minecraft.
- Weighted skeletal skinning с несколькими влияниями костей на вершину.
- Гуманоидный риг с отдельными сегментами позвоночника, плечевого пояса, рук, кистей и пальцев, таза, ног, шеи и головы.
- Face rig: контроллеры глаз, век, бровей и челюсти плюс morph targets (blend shapes) для выражений и артикуляции речи.
- Дополнительные кости и контроллеры для прядей волос, лент, подвесок и подвижных частей одежды.
- Socket/attachment точки для предметов и эффектов.

Количество костей и morph targets определяется реальной моделью и профилированием; не задавать искусственный фиксированный лимит до тестов.

### Анимация и motion control

Персонаж использует гибридную систему:
1. Авторские keyframe-анимации для походки, бега, поворотов, жестов, реакций и выразительных действий.
2. Animation state machine, crossfade, layer masks и additive layers.
3. Процедурные контроллеры: gaze/look-at, IK рук и ног, корректировка стоп к поверхности, баланс корпуса, повороты головы и микродвижения.
4. Эмоциональные параметры и facial controller, не привязанные жёстко к одному animation clip.
5. Отдельный lip-sync слой для речи.

LLM выдаёт смысловое намерение и состояние, но не координаты каждой кости. Локальный Motion Controller преобразует намерение в позу и последовательность визуальных/игровых команд.

### Физика

Цель — выразительная, художественно настроенная физика в духе ZZZ, а не полная физическая симуляция каждой вершины.

Предусмотреть:
- spring/damped dynamics для прядей волос, хвостов, лент и подвесных элементов;
- skeletal secondary motion для частей одежды;
- ограниченную cloth-подобную симуляцию там, где она действительно нужна;
- коллизии с упрощёнными capsule/sphere/plane-представлениями тела и окружения;
- ограничения диапазона, затухание, фиксацию при резких позах и детерминированное восстановление после паузы/выгрузки;
- ручную художественную коррекцию и авторские анимации для сложных action-сцен.

Одна физическая симуляция не заменяет работу аниматора. В качестве ориентира использован опубликованный в интервью комментарий команды анимации ZZZ: волосы были названы одной из главных технических сложностей; команда описала Maya Dynamics Evaluator, интеграцию с skinning, использование лёгких сторонних инструментов для простых сцен и ручную покадровую настройку сложных action-сцен. Источник: [Inside Games, интервью команды ZZZ, 2024-12-12](https://s.inside-games.jp/article/2024/12/12/162341.html).

### Формат ассетов

- Blender — основной authoring tool.
- GLB/glTF 2.0 — предпочтительный runtime interchange format при условии подтверждённой поддержки всех нужных функций.
- Исходные Blender-файлы хранятся отдельно от runtime Content Pack; в игре загружается экспортированный asset.
- Для VRM возможен отдельный импортный конвертер, но VRM не является обязательным runtime-контрактом.
- Rig descriptor / sidecar metadata может описывать имена костей, semantic tags, spring chains, collision proxies, facial channels и attachment sockets.

### Рендерер

Конкретная библиотека сейчас **не утверждается**. Кандидаты для технического spike:
- [GemRender](https://github.com/Warfactory-Official/GemRender) — GLTF, GPU skinning, morph targets и animation blending; есть таргет Fabric 1.21.1, но проект молодой, требует проверки API, лицензии, зависимостей и реальной поддержки динамического управления facial morph weights. GemRender сам по себе не предоставляет полноценную ZZZ-подобную physics-систему.
- [BlendLib](https://github.com/LIy-hub/BlendLib-Public) — Fabric GLB pipeline со skinned assets и pose/animation API. Документированный strict v1 не поддерживает morph targets/shape keys, выполняет CPU skinning, ограничивает skin до четырёх влияний на вершину и требует bake для физических эффектов/процедурных модификаторов. Поэтому в текущем описанном профиле BlendLib не закрывает все требования самостоятельно.
- Собственный GLB renderer или отдельный слой расширения — резервный путь, если готовые библиотеки не дают нужный контроль.

[GeckoLib](https://github.com/bernie-g/geckolib) может использоваться для вспомогательных кубических моделей и эффектов, но не является целевым renderer для основной гладкой polygon-mesh модели.

Перед фиксацией зависимости нужно собрать тестового персонажа и проверить полный pipeline на точном Fabric 1.21.1.

## Где выполняется симуляция

- Хост остаётся авторитетным для AI, решений, навигации, игровых действий, hitbox и взаимодействия с миром.
В соответствии с последующим решением [ADR-0007](ADR-0007-procedural-motion-engine.md), все вычисления движения и secondary physics, определяющие состояние персонажа, выполняются на хосте. Клиенты получают серверные pose snapshots и интерполируют их только для отображения; независимая клиентская симуляция движения/физики не является источником состояния.

## Проверка renderer поэтапно

Не превращать весь целевой профиль качества в условие первого прототипа. Проверять renderer по нарастающей:

1. **Первый spike:** загрузить готовую модель, проверить skinning и возможность воспроизводить клип или программно менять позу.
2. **Следующий рабочий этап:** проверить blending/layers, доступ к костям, базовый look-at и IK.
3. **По мере подключения функций:** проверить facial morphs/visemes, secondary physics, сложные жесты и синхронизацию на нескольких клиентах.
4. **Перед финальным релизом полной версии:** проверить целевой визуальный профиль на выбранных финальных моделях и реальной нагрузке.

Для первого spike достаточно понять, подходит ли библиотека как основа следующего шага. Её выбор остаётся предварительным, пока не проверены функции, которые реально понадобятся продукту. Не требуется реализовать весь Motion Engine, мимику, одежду и физику, прежде чем получить первый отображаемый игровой персонаж.

## Последствия

- Фаза 0 проверяет самый короткий путь загрузки модели и управления позой; расширенные проверки renderer проводятся тогда, когда для них появляется реализация.
- Для финальных моделей важны подходящая topology, skin weights и необходимые facial channels; недостающие возможности можно оценить и адаптировать, не создавая модель с нуля.
- Нужны отдельные authoring и runtime-пакеты ассетов.
- Профилирование GPU/CPU нужно при появлении заметной нагрузки и перед финальным релизом; не оптимизировать заранее без измерений.
- Выбор renderer и физического backend будет закреплён отдельным ADR после проверки прототипа.

## Открытые вопросы

- Достаточен ли GemRender API для runtime-driven morph target control, IK и кастомных spring systems?
- Можно ли расширить выбранный renderer без форка и без лицензионно неприемлемого связывания?
- Какая физическая модель даёт нужный результат при разумной стоимости: Verlet-based spring chains, XPBD constraints, skeletal dynamics или сочетание?
- Как синхронизировать визуальное состояние между клиентами при разной частоте кадров?
- Какой профиль материалов лучше передаёт anime-art direction без чрезмерной нагрузки на GPU?
