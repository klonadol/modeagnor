# ADR-0009: План по зависимостям и завершённым вертикальным срезам

- **Статус:** Accepted — пересмотр планирования по прямому запросу пользователя 2026-11-05.
- **Дата:** 2026-11-05, Asia/Vladivostok (UTC+10).
- **Область:** порядок реализации, staged activation, критерии готовности.
- **Частично заменяет:** фазовые предписания ADR-0003/0004/0005/0006/0007/0008 и прежней части A Blueprint. Платформа, host authority, пять агентов, шесть stores, 3D quality и правила ассетов сохраняются. Прежний маршрут сохранён в [архиве](../archive/ROADMAP_2026-11-04.md).

## Причина

Прежняя фаза 0 требовала renderer/IK/gait/physics/двухклиентский pose demo до Character Runtime, хотя те же работы входили в фазу 3. Общий exit «подтверждённые технические ограничения» не ограничивал объём. Поздний диалог зависел от готового 3D. Runtime feedback между cognitive workers ошибочно превращался в запрет частичной функциональной приёмки. Skill закреплял эти gates; его ссылка Fabric Networking содержала пробел.

## Решение

1. ROADMAP — единственный порядок и exit criteria; Blueprint сохраняет подробную техническую спецификацию. Требования и архитектурные инварианты не заменяются дорожной картой.
2. P0 ограничена проверенным bootstrap. По локальным свидетельствам её новый scope завершён; прежний широкий prototype не объявляется выполненным.
3. Storage backend решается перед первой сохраняемой NPC (P1.1). Renderer/формат проверяется перед первым 3D-срезом (P3.1). Такой перенос не меняет принятые границы владения данными или pose.
4. NPC runtime/placeholder → dialogue/history → 3D/presentation → external packs → память/контекст → cognitive loop → действия → голос → standalone release → мир/addons. Voice не имеет технической зависимости от автономности; это рекомендуемый порядок работ.
5. А — проверка текущего кода; Б — ограниченный риск текущего решения; В — интеграция после появления участников. В не блокирует ранний этап.
6. Store создаётся с реальным writer. Runtime cycles строятся по snapshots и событиям, компоненты принимаются завершёнными ограниченными срезами. Полная фаза всё равно требует общего пользовательского сценария.
7. Dialogue сохраняет History+event атомарно, но consumer deliveries/leases/tasks создаёт при активации consumer. Protected replay sources не удаляются по recent-N; удаление приватных данных имеет явный SOURCE_DELETED outcome. Это уточняет staging, сохраняя независимые ack и restart guarantees ADR-0004.
8. Открытые решения закрываются перед первым потребителем. Нет недельного универсального renderer/physics gate. Нельзя назвать свой renderer доказанным решением, если кандидаты не проходят тест.

## Альтернативы и последствия

Сохранение прежней P0 продолжало бы дублирование будущей реализации. Удаление 3D/authority требований упростило бы работу ценой цели проекта — отвергнуто. Новый порядок раньше даёт реальные пользовательские результаты, но не отменяет сложность конечного motion/physics/AI комплекса. P3/P6/P7 крупные по предмету, поэтому внутри каждой есть отдельно проверяемые срезы. Library compatibility, pose budgets, storage driver и provider capabilities остаются измеряемыми рисками своих задач.

Код, сборочная конфигурация и исходные runtime evidence этим решением не меняются. Исторические отчёты сохраняют старую нумерацию и не являются инструкциями продолжения. Трассировка каждой старой задачи — [матрица](../PLAN_MIGRATION.md).
