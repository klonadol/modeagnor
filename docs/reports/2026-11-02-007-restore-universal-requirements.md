## 1. Причина

Пользователь уточнил, что предыдущее упрощение требований было ошибочным: контроль прогресса, универсальность архитектуры и предварительная проработка технических нюансов должны сохраняться. Упрощать следует только ненужные ограничения вокруг временных локальных материалов, не ослабляя целевую полноту системы.

Отдельно зафиксировано ограничение квоты GitHub Actions artifacts: генерировать/загружать artifacts только при необходимости ручной проверки человеком.

## 2. Восстановлено

- Восстановлен полный roadmap Фаз 0–11, включая подробные задачи и критерии Фаз 3–9, которые ранее были случайно удалены из roadmap.
- Возвращены полный список технических проверок раннего прототипа и требования к renderer, skeletal rig, facial channels, IK, procedural motion, secondary physics и multiplayer pose sync.
- Возвращено требование capability profile для каждой импортируемой модели.
- Восстановлены расширенные требования к Content Packs: проверка манифестов, путей, размеров, типов, версий/checksum, ZIP path traversal и безопасной сетевой синхронизации.
- Возвращён стабильный и документированный универсальный Interaction API до разработки первого addon.
- Восстановлены подробные критерии качества персонажей, физики и renderer spike.
- Возвращены подробные правила отчётности, журналирования и шаблонов: отчёт на каждую завершённую логическую задачу, фиксация проверок и результатов, ADR для архитектурных решений.
- Восстановлена расширенная Asset Replacement Register с источником, прямой ссылкой, локальным путём, автором, датой, SHA-256, статусом прав и планом замены.

## 3. Сохранено из отдельных согласованных решений пользователя

- Временные модели можно использовать в локальных dev-сборках, локальных JAR и локальных Content Packs.
- Сами такие файлы не коммитятся в публичный Git, не попадают в публичные релизы и не раздаются другим игрокам.
- Замена временных моделей требуется только перед финальным релизом полной версии после переноса авторского мира в Minecraft (Фаза 11). Первый companion-релиз (Фаза 10) не блокируется.
- Если у источника есть прямая ссылка на скачивание, её следует использовать и сохранять в реестре.
- Базовая безопасность API-ключей, данных игроков, серверных действий и публичного распространения сохраняется.

## 4. Политика GitHub Actions artifacts

В `docs/INDEX.md` добавлено отдельное правило:
- Не загружать artifacts на каждый CI run.
- Создавать artifact только когда человеку требуется вручную открыть/скачать/проверить результат (например JAR, скриншоты, видео или диагностический пакет).
- Для обычного CI использовать check status, job logs, test output и job summary.
- Если artifact нужен, прикладывать только минимальный набор файлов; не включать секреты, личные данные или временные модели.

В текущем дереве репозитория workflow-файлы GitHub Actions отсутствуют, поэтому правило пока документировано, но не применяется к существующему workflow.
